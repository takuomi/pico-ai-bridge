# Pico AI Bridge

Use `pico_server_info` for connectivity and version, name, build, and bundle identifier, `pico_list_models` for models, `pico_responses`, `pico_chat_completions`, or `pico_ollama_chat` for generation, and `pico_compare_models` for sequential comparisons of at least two models. Generation `model` is optional. The list merges `/v1/models` and `/api/tags` by name, treating untagged names as `:latest`; `include_capabilities` calls `/api/show` once per merged model, using the tag name or the `id` when no tag name exists. Default entries include `id`, `name`, `tag_model`, `created`, `owned_by`, `display_name`, `status`, and tag metadata. Only with `include_capabilities: true`, a successful show adds `capabilities` and `context_length`, while a Pico HTTP error adds `capabilities_error: {source, status, body}`; listing HTTP errors appear as `{path, error: {source, status, body}}` in `partial_errors`. If both listing endpoints fail, the result is `{models: [], partial_errors}` with `isError`.

All tools accept `raw: true` for HTTP status and parsed Pico body (text when not JSON), with the configured API key redacted in Pico values and keys. Raw listing returns `v1_models`, `api_tags`, and optionally `api_show` keyed by the name sent to `/api/show`. Chat requires `prompt` or `messages` sent as given, images, or `system` alone, which sends only a system message; `extra.messages` also supplies input when none of these is given; Ollama accepts the same inputs or omits `messages`; comparison accepts exactly one of `prompt` or `messages`, or `images` alone, sends a supplied `messages` array as Responses `input` with `api: "responses"`, and maps comparison `system` to Responses `instructions`; Responses accepts optional string or item-array `input` sent as given, plus `instructions`, and has no `messages` argument. With no input, it omits the field and passes Pico's result through. Ollama likewise omits absent `messages` and passes Pico's result through; the tested Pico server returns HTTP 400 for these requests. Images attach to the last user message; string content becomes text and image parts, array content gains image parts, and Ollama appends base64 images. An entry starting with `data:`, `http://`, or `https://` (ASCII case-insensitive, no leading whitespace) is a URI; anything else is a local file path. `~` and paths starting with `~/` are resolved against the home directory of the bridge process; other paths are used as given (relative paths resolve against its working directory). After classification, Ollama parses each data URI as a URL, removing ASCII tabs and newlines and trimming surrounding C0 controls and spaces, then removing its fragment before finding the first comma and percent-decoding the payload to bytes, then decoding forgiving-base64 when the trimmed media type ends in `;` followed by optional spaces and then `base64` (case-insensitive). ASCII whitespace and optional padding are accepted; the resulting bytes are sent as standard base64. A percent sign without two ASCII hex digits remains a literal byte. Invalid URLs, missing commas, and invalid base64 return `invalid_arguments`. Image-only input sends a user message containing images. Other content shapes fail before image reads. With Ollama images, an existing non-array `images` field on the target user message also fails before image reads. Local paths are read without image-type checks; URLs pass through.

Chat `response_format`, Responses `json_schema` with required `json_schema_name` as `text.format: {type: "json_schema", name: json_schema_name, schema: json_schema}`, and Ollama `format` pass to Pico; answers are not schema-checked. Responses `previous_response_id` passes through. POST tools send `stream: false`, and conflicting `extra` fields return `invalid_arguments` before image reads or requests. Default chat returns the first choice; Responses joins all `output_text` parts in output order; Ollama uses `message.content`. Chat and Responses results and comparison rows include `refusal` (null when absent); Responses joins refusal parts in output order. Ollama comparison rows always include `usage: {prompt_eval_count, eval_count}` with nulls for absent counts. Results include reasoning, response model, finish reason or status, chat/Responses `response_id`, usage or durations with nulls for absent values, API timestamps, and API-specific calls. Chat function calls return `{id, type, name, arguments}`; custom calls return `{id, type, name, input}` with free-text input. Responses always returns `function_calls` and `custom_tool_calls` arrays; custom entries use `{id, call_id, name, input, status}` with null for absent id or status. Chat uses `created`; Responses uses `created_at` and `completed_at`; Ollama uses `created_at`. Responses includes `usage.cached_tokens`, `error`, and `incomplete_details`; Ollama includes `durations_ms`, `created_at`, and `done`. Comparison rows include the applicable fields, `model`, `elapsed_ms`, or a per-row error. Comparison accepts images alone and sends an image-only user message. Responses comparison rows also include `error` and `incomplete_details`, each null when absent from Pico. In default mode, every Pico response field used to extract or compute a result must have its expected JSON type when present and non-null; malformed fields return `unexpected_response` with the endpoint message. Absent or null optional fields remain null. Comparison rows use the same checks. Raw mode returns parsed Pico bodies after API key redaction, or the original text if parsed JSON contains a non-finite number or unsafe integer. Default mode reports `response_parse_failed` for such a 2xx body; Pico HTTP errors keep the original text. Default mode checks 2xx response shapes. Chat requires a nonempty `choices` array whose first item has a message with string `role`; `content` may be a string (including an empty string), null, or absent, and null or absent content gives an empty answer. Chat `refusal` may be string, null, or absent. `reasoning_content` and `reasoning` may each be a string, null, or absent. Chat `tool_calls` may be an array, null, or absent; each item needs string `id` and `type`. A custom item needs object `custom` with string `name` and free-text string `input`; other types need object `function` with string `name` and string `arguments`. Ollama requires a message with string `role`; `content` must be a string (including an empty string); `thinking` may be a string, null, or absent. Ollama `tool_calls` may be an array, null, or absent; each item must be an object with an object `function` and string `function.name`; `function.arguments` may be absent, null, an object, or a string, with absent or null extracted as null. Responses requires an `output` array of objects with string `type`; each item's `content` and `summary` may be arrays, null, or absent, with object parts that require a string `type`; `text` may be a string, null, or absent, except `output_text`, `summary_text`, and `reasoning_text` require string `text`, and `refusal` requires string `refusal`. A `function_call` item requires string `name`, `call_id`, and `arguments`. A `custom_tool_call` item needs string `name`, `call_id`, and free-text `input`, plus string `id` and `status` when present. Malformed success returns `unexpected_response`. Unused fields, later chat choices, semantic relationships, and argument contents are not validated. `split_thinking: false` keeps inline `<think>` text; separate reasoning fields still apply. Chat and Responses pass `reasoning_effort` as `reasoning_effort` and `reasoning.effort` respectively. Ollama `think` accepts a boolean; `extra.think` sends a level string or null unchanged, and the tested Pico server rejected level strings. Comparison `reasoning` applies only to chat and Responses; `think` and `options` apply only to Ollama. Inapplicable arguments, or Ollama `options.num_predict` with `max_tokens` and `options.temperature` with `temperature`, return `invalid_arguments`.

For Chat Completions tool-result follow-ups, replay the assistant `tool_calls` with JSON-string `function.arguments` and add a tool message with the matching `tool_call_id`; the bridge parses valid returned argument JSON into a JSON value.

Unsafe integers anywhere in caller arguments return `invalid_arguments`; Pico bodies with such integers retain source text in raw and HTTP error results, while default 2xx results return `response_parse_failed`. Tool-call argument JSON with unsafe integers remains text. Pico HTTP errors retain status and body. In default model listing, `/v1/models` `data` items need string `id` and, when present, a `status` object whose `value` is a string when present and non-null; an absent or null `value` extracts as null. A successful `/api/show` body needs to be an object; present `capabilities` must be an array of strings, present `model_info` must be an object, and present `.context_length` must be a finite number. Absent or null optional fields remain null. Malformed shapes return `unexpected_response`; raw listing preserves the Pico bodies. In default mode, a present `/api/tags` `size` or Ollama duration must be a finite number; malformed values return `unexpected_response`. Bridge errors include `invalid_configuration`, `invalid_arguments`, `unknown_tool`, `connection_failed`, `timeout`, `image_read_failed`, `response_parse_failed`, `unexpected_response`, and `internal_error`. A queued request that times out is never sent. A timeout after sending returns an error while the request holds its FIFO permit until Pico finishes and its body is read. Comparison records that timeout and waits for the request to finish before sending the next model, even with concurrency above one; MCP cancellation ends the wait while the sent request retains its permit. MCP request IDs and cancellation request IDs accept strings or safe integers. Cancellation removes queued requests only; sent requests are never aborted because testing found that closing a generating connection was followed by Pico stopping on the next generation request. `PICO_TIMEOUT_MS` is an integer from 1 through 2147483647. `PICO_MAX_CONCURRENT_REQUESTS` is a safe integer of at least 1. Redirects are not followed.
