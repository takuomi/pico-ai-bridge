# Architecture

This project is a bridge between Claude and the configured Pico AI Server. Every tool accepts `raw` to return the HTTP status and parsed Pico body, or text when the body is not JSON. The configured API key is redacted in raw Pico body values and keys. Default mode extracts useful common fields. Every Pico response field used to extract or compute a result must have its expected JSON type when present and non-null; malformed fields return `unexpected_response` with the endpoint message. Absent or null optional fields remain null. Comparison rows use the same checks. Raw mode returns parsed Pico bodies after API key redaction, or the original text if parsed JSON contains a non-finite number or unsafe integer. Such 2xx bodies return `response_parse_failed` in default mode; Pico HTTP errors keep the original text. Tool-call argument JSON with an unsafe integer stays as text. On POST tools, `split_thinking` defaults to `true`: first, if the first closing `</think>` in the text has no opening `<think>` before it, the trimmed text before that tag is reasoning and processing continues with the text after it; then every `<think>...</think>` pair is removed and its trimmed text is added as reasoning. Empty reasoning parts are dropped and the rest joined with `\n`. Set `split_thinking` to `false` to leave the answer untouched. Reasoning Pico returns in separate fields is always used. Responses reasoning items use `summary` when it is non-empty and `content` otherwise. An unclosed `<think>` and any other format stay in the answer and are not reported as reasoning. POST tools accept `extra` for top-level fields that do not conflict with fields built from other arguments. Conflicts return `invalid_arguments` before images are read or a request is sent. The model argument is optional for generation; when omitted, the request has no model field unless `extra.model` supplies one, and Pico applies its default. Comparison is a separate opt-in tool. `reasoning_effort` is sent unchanged, as `reasoning_effort` in chat completions and as `reasoning.effort` in Responses. In `pico_compare_models`, `reasoning` is sent the same way for those APIs. Ollama `think` accepts a boolean, and `extra.think` sends a level string or null unchanged (the tested Pico server accepted null and rejected level strings). `think` is boolean-only because, in testing, Claude Desktop chat (with Sonnet 5.5 and Opus 5.5) sent `true` as the string `"true"` when `think` also accepted strings, while Claude Code sent a boolean. Comparison `think` and `options` apply only to Ollama. Comparison rejects `reasoning` for Ollama and `think` or `options` for other APIs with `invalid_arguments`. For Ollama, `options.num_predict` conflicts with `max_tokens`, and `options.temperature` conflicts with `temperature`. User configuration contains only connection and environment settings.

`server/core/` owns configuration, argument validation, image path conversion, redaction, and the plain-object tool registry. Arguments that accept several JSON types declare a `type` array rather than `oneOf`. Both are valid JSON Schema; this is a tested interoperability choice, not an MCP requirement: Claude Desktop listed a `oneOf` argument as `any`, and with type arrays it listed each type and sent objects, arrays, and numbers with their JSON types. Numeric arguments require finite numbers and safe integers, and a non-finite number or unsafe integer anywhere in the arguments (including free-form objects such as `extra`, `messages`, `tools`, and `options`) is rejected because JSON would lose its value; invalid values return `invalid_arguments` before Pico requests. `server/pico-client.js` owns HTTP, body parsing, timeout coverage, redirect handling, and a FIFO semaphore spanning the request and body reading. A redirect is returned as a Pico HTTP error without following its Location. Cancellation removes a queued request before it is sent. A queued request that reaches its deadline also times out without being sent. Once sent, a request is never aborted. An individual request returns its timeout error promptly, with a non-enumerable `settled` promise that resolves after Pico finishes and the permit is released; error data omits this property. Comparison records the timeout row and awaits `settled` before the next model, including when the concurrency limit exceeds one, so its result can arrive later than the individual timeout. MCP cancellation ends that wait and the comparison, while the sent request keeps running. The request keeps its FIFO permit until Pico finishes and the body is read. Closing a connection while Pico was generating was followed by the server stopping on the next generation request in testing. The default concurrent request limit is one because loading several large models at once can exhaust a Mac's memory. Each file in `server/tools/` defines one tool. Pico HTTP errors pass through with their status and body; bridge failures use explicit bridge error kinds. No Pico error text is classified. Supplying both `prompt` and `messages` to chat or Ollama returns `invalid_arguments`. Responses accepts `input` as a string or item array and has no `messages` argument. When `input` is absent, it is omitted from the request and Pico's result passes through; Ollama likewise omits absent `messages` and passes Pico's result through (this Pico returns HTTP 400). In default mode, generation returns `unexpected_response` for a 2xx body without the expected shape. Chat completions require a nonempty `choices` array whose first item has a message with string `role`; its `content` may be a string (including an empty string), null, or absent, and null or absent content gives an empty answer. Chat `refusal` may be string, null, or absent. Its `reasoning_content` and `reasoning` may each be a string, null, or absent. Chat `tool_calls` may be an array, null, or absent; each item must be an object with string `id` and string `type`. A `custom` item needs an object `custom` with string `name` and free-text string `input`; other types need an object `function` with string `name` and string `arguments`. Responses require an `output` array of objects with string `type`. Their `content` and `summary` may be arrays, null, or absent; each array part must be an object with a string `type`; its `text` may be a string, null, or absent, except `output_text`, `summary_text`, and `reasoning_text` require string `text`, and `refusal` requires string `refusal`. A `function_call` item requires string `name`, `call_id`, and `arguments`. Ollama requires a message with string `role`; its `content` must be a string (including an empty string); `thinking` may be a string, null, or absent. Ollama `tool_calls` may be an array, null, or absent; each item must be an object with an object `function` and string `function.name`; `function.arguments` may be absent, null, an object, or a string, with absent or null extracted as null. Unused fields, later chat choices, semantic relationships, and argument contents are not validated. Empty answers from correctly shaped bodies are valid; raw mode returns parsed bodies with the configured API key redacted in values and keys. Model extraction returns `unexpected_response` if a successful `/v1/models` body is not an object with a `data` array of objects with string `id` fields and, when present, a `status` object whose `value` is a string when present and non-null (an absent or null `value` extracts as null), or a successful `/api/tags` body is not an object with a `models` array of objects with a string `name`. The optional `/v1/models` `models` field must be an array of objects when present. Raw listing without `include_capabilities` returns those bodies without extraction. With `raw` and `include_capabilities`, 2xx listings need only arrays of objects with string `id` or `name` so `/api/show` can be called; `status`, `size`, and other fields are not validated. With `include_capabilities`, absent or null `capabilities` and `context_length` remain `null`. In default mode, a successful `/api/show` body that is not an object, a present `capabilities` that is not an array of strings, a present `model_info` that is not an object, or a present `.context_length` that is not a finite number returns `unexpected_response`. In default mode, a model whose `/api/show` request returns a Pico HTTP error has `capabilities_error: {source: "pico", status, body}`, and the other models are still listed. A present `/api/tags` `size` and present Ollama duration fields must be finite numbers; malformed values return `unexpected_response` in default mode. A listing endpoint that returns a Pico HTTP error appears in `partial_errors` as `{path, error: {source: "pico", status, body}}` alongside models from the other endpoint. A connection failure or timeout on any `pico_list_models` request, including `/api/show`, returns a single bridge error; in default mode, so does a successful body that is not valid JSON. Server information includes `bundle_identifier` and uses `null` for absent name, version, build, or bundle identifier and does not infer API support from the version; in default mode, a successful `/api/version` body that is not an object returns `unexpected_response`. Configuration validation rejects malformed or non-HTTP base URLs, credentials, queries, or fragments in the URL, timeout values outside the integer range 1 through 2147483647 ms, and concurrency values that are not safe integers of at least 1 on every tool call without contacting Pico. Empty or unsubstituted numeric settings use defaults.

Models merge by Ollama name, treating an untagged name as `:latest`. Each default entry has `id`, `created`, and `owned_by` from `/v1/models` `data`, `name` and `tag_model` from `/api/tags`, `display_name` from the optional `/v1/models` `models` array, `status` from `status.value`, and tag metadata (`format`, `family`, `parameter_size`, `quantization_level`, `size_bytes`, `modified_at`); `size_gb` is bytes divided by 1e9 and rounded to two decimals. With capabilities, `/api/show` runs once per merged model using its tag name or its `id` when absent from tags; raw `api_show` uses that sent name as its key. If both list endpoints fail, default mode returns `{models: [], partial_errors}` with `isError`.

Chat and Ollama message items and Responses input items are sent as given. Comparison accepts exactly one of `prompt` or `messages`, or `images` alone; with `api: "responses"`, a supplied `messages` array is sent as `input`, `system` becomes `instructions`, and images attach to the last user message. Images attach to the last user message: string content becomes text and image parts, array content gains image parts, and Ollama gains base64 strings in `images`. An entry starting with `data:`, `http://`, or `https://` (ASCII case-insensitive, no leading whitespace) is a URI; anything else is a local file path. `~` and paths starting with `~/` are resolved against the home directory of the bridge process; other paths are used as given (relative paths resolve against its working directory). After classification, every Ollama data URI is parsed as a URL, removing ASCII tabs and newlines and trimming surrounding C0 controls and spaces; its fragment is then removed before the first comma is found, and the payload is percent-decoded to bytes. If the ASCII-whitespace-trimmed media type ends in `;` followed by optional spaces and then `base64` (case-insensitive), forgiving-base64 decodes those bytes, accepting ASCII whitespace and optional padding. The resulting bytes are encoded as standard base64. A percent sign without two ASCII hex digits remains a literal byte. Invalid URLs, missing commas, and invalid base64 return `invalid_arguments`. Image-only calls, including an empty `messages` or `input` array, send one user message containing only images. Chat and Ollama calls with `system` alone send only a system message; comparison still requires a prompt, messages, or images. Other content shapes fail before image reads. For Ollama images, an existing non-array `images` field on the target user message also fails before image reads. Chat `response_format`, Responses `json_schema` with required `json_schema_name` as `text.format: {type: "json_schema", name: json_schema_name, schema: json_schema}`, and Ollama `format` are sent to Pico; answers are not checked against schemas. Responses `previous_response_id` is sent as given. All POST tools send `stream: false`, so `extra.stream` conflicts. Default chat selects the first choice; Responses concatenates all `output_text` parts in output order; Ollama uses `message.content`. Results include reasoning, response model, API-specific finish reason or status, response ID for chat and Responses, API timestamps, usage or durations with nulls where absent, and normalized calls. Chat `tool_calls` contain `{id, type, name, arguments}` for function items and `{id, type, name, input}` for custom items; custom input stays free text. Responses always includes `function_calls` and `custom_tool_calls`, each an array, and custom entries contain `{id, call_id, name, input, status}` with null for absent id or status. Chat uses `created`; Responses uses `created_at` and `completed_at`; Ollama uses `created_at`. Ollama results also include `created_at` and `done`; Responses results include `usage.cached_tokens`, `error`, and `incomplete_details`. Comparison rows include model, answer, reasoning, response model, calls, finish reason or status, `response_id` and `created` for chat, `response_id`, `created_at`, and `completed_at` for Responses, or `durations_ms`, `created_at`, and `done` for Ollama, usage when present, elapsed milliseconds, or a row error. Responses comparison rows also include `error` and `incomplete_details`, each null when absent from Pico. Default validation accepts Chat custom items only with string id, name, and input, while other Chat types retain the function rules; Responses custom items need string name, call_id, and input, with optional string id and status. Malformed items return `unexpected_response`.

Pico-derived values are extracted from the unredacted Pico body, then the configured API key is redacted in those values and in keys only of Pico objects returned as-is (raw bodies, Pico error bodies, chat/comparison `usage`, Responses `error` and `incomplete_details`, tool-call arguments, `pico_list_models` model fields, and `api_show` model-id keys). Field names the bridge builds are never changed. Runtime error details, unexpected internal errors, and logs are redacted; caller arguments and configuration values remain intact.

Base URL validation rejects non-HTTP(S) or unparsable URLs, including values without a scheme such as `localhost:7426`, which parses with `localhost:` as its scheme; credentials; and any query or fragment, including bare `?` or `#` delimiters. Such values cannot address Pico's API paths or would send requests elsewhere. Validation does not check reachability.

## Not exposed

No tools are provided for `/api/generate`, embeddings, `/v1/completions`, streaming, or model management (pull, push, create, copy, delete, blobs). `/api/ps` is also not exposed: on the tested server it listed every installed model with changing `expires_at` values whether or not the model was loaded, so its meaning is unclear. Model load state is reported from `/v1/models` `status.value`.

## Protocol adapters

`server/adapters/stdio-jsonrpc.js` is the shipped zero-dependency stdio adapter. JSON-RPC request IDs and cancellation `requestId` values may be strings or safe integers; the adapter rejects fractions, unsafe integers, null, and other types. A legacy `initialize` request selects handshake semantics and negotiates one of `2025-11-25`, `2025-06-18`, `2025-03-26`, or `2024-11-05`. A request with the 2026-07-28 `_meta` envelope uses modern stateless semantics. Modern requests require the protocol version and client capabilities; unsupported versions return `-32022` with the requested and supported versions. `server/discover` advertises tools and only `2026-07-28` as a version usable in subsequent requests; modern `-32022` errors likewise list only `2026-07-28`. The four legacy revisions remain available through `initialize`. After negotiating 2025-03-26 or 2024-11-05, stdio accepts JSON-RPC batches: an empty batch gets one `-32600` error, other batches get one response array when replies remain after excluding notifications and cancelled requests, otherwise no output, an initialize element gets `-32600`, and each modern-era request element gets `-32600` (modern notifications get no reply). Array lines remain invalid before initialize, under 2025-06-18 or 2025-11-25, and for modern per-request handling. Each request uses its own `_meta` for modern handling. A request with present non-object `params._meta` returns `-32602` in either era. Legacy requests without modern metadata need a successful legacy `initialize` on the connection, except `ping`; legacy `initialize` remains available after modern requests. Modern list results include `resultType`, `ttlMs`, and `cacheScope`; `nextCursor` is absent because all six tools fit on one page. Modern call results include `resultType`. Legacy results omit these modern fields. A modern `subscriptions/listen` request is acknowledged with an empty honored filter because the tool list does not change at runtime. Legacy `ping` returns an empty result, including before `initialize`; modern `ping` is removed by the 2026-07-28 protocol. In both eras, `notifications/cancelled` identifies the request through `params.requestId`. The stdio adapter signals queued work to stop and suppresses the cancelled request response. A `notifications/cancelled` whose `requestId` is a `subscriptions/listen` request ID removes that subscription without sending a completion for it. When stdin closes, each remaining subscription receives a result with `resultType: "complete"` and its subscription ID in `_meta`.

`server/adapters/sdk.js` maps the same registry to `@modelcontextprotocol/server` v2.1.0, passes the handler context abort signal to tool calls, and uses its `serveStdio` dual-era entry. SDK modules are injected by `dev/sdk-entry.js`, so nothing under `server/` imports the package. `server/index.js` selects the shipped adapter.

## Conformance

`dev/conformance.test.js` runs the same assertions against both stdio entries through the official `@modelcontextprotocol/client` v2.1.0. It exercises legacy-only, modern-pinned, and dual-era auto-detect modes, checking the negotiated era, tool metadata, successful and invalid calls, unknown-tool errors, raw mode, legacy ping, and modern subscription behavior against a local mock Pico HTTP server. The conformance suite also sends raw stdio initialize requests for each advertised legacy version, then validates tools/list and pico_server_info results with SDK schemas; for 2025-03-26 and 2024-11-05 it also sends a batch and validates both batch replies, and for 2025-06-18 and 2025-11-25 it checks that the same array line receives `-32600`. `dev/modern.test.js` replays the Claude Desktop discover-then-list sequence and validates both results with the SDK client's `specTypeSchemas`. `npm test` runs the sorted `test/*.test.js` files; `npm run test:conformance` runs the sorted `dev/*.test.js` files. Both fail when no files are listed. `test/tools-contract.json` records the six public tool definitions checked by unit and adapter conformance tests; `npm run test:live` runs `test/live.js` against `PICO_BASE_URL`. The live test starts the shipped `server/index.js` stdio server, sends a legacy `initialize` and calls each of the six tools with integer IDs, including default and raw generation through all three APIs, checks their results, and checks for a clean exit. It also uses 2026-07-28 per-request metadata without `initialize` to discover the server, list six tools, and run generation through each of the three APIs over the shipped stdio server. It also checks GET tools and merged capabilities, default and raw generation through all three APIs, tool calls and tool-result round trips, JSON formats, instructions, `extra`, `keep_alive`, `previous_response_id`, image input shapes, reasoning effort, inline thinking, Pico errors, and sequential comparison. A live comparison with a 1000 ms timeout and concurrency of two uses a local forwarding proxy to record chat request arrival and response completion, then checks that the second request arrives after the first response finishes. Structured-output formats, `keep_alive`, and `previous_response_id` are live acceptance checks showing Pico accepted the request; unit tests assert exact outgoing fields. The root unit suite covers tool behavior and stdio framing without SDK dependencies. The release workflow runs unit and conformance tests, builds both archives, and runs archive-level verification on Linux, macOS, and Windows. `scripts/smoke-artifacts.py` extracts each archive, substitutes the manifest's declared command, arguments, and environment values, then runs `initialize` and `pico_server_info` against a local mock Pico. It does not install either archive in Claude Desktop or Claude Code. Publication waits for all three archive verification jobs; the publishing job also keeps version matching, checks, packaging, and archive verification.

Live tests use `PICO_TEST_TOOLS_MODEL` and `PICO_TEST_VISION_MODEL` (both default to `Qwen3-VL-2B-Instruct-4bit`) and `PICO_TEST_THINKING_MODELS` (a comma-separated list, default `LFM2.5-1.2B-Thinking-4bit`). `deepseek-r1-distill-qwen-1.5b-4bit` is not a default because on the tested server its `/api/chat` replies sometimes ran for about two minutes and ended without a `message`. Other servers may behave differently. At least two distinct role models are required. All distinct models run generation through the three APIs in default and raw modes with temperature 0 and a 4096-token limit. Comparisons run sequentially with temperature 0 and a 3072-token limit in default and raw modes for all three APIs. Additional default comparisons for all three APIs supply `messages: [{role: "user", content: prompt}]` with temperature 0 and a 1024-token limit, checking each row for an answer and no error. A default chat image comparison uses the generated red PNG and the vision and tools models (repeating the vision model if they match) with the same settings and row checks. Temperature 0 keeps small thinking models from sometimes running away. Tool-call, vision, and thinking behavior is asserted directly on the assigned role model without capability gating or retries. Vision uses a temporary generated red PNG. Prompted calls expect the answer to name red; image-only calls require a nonempty answer. Responses `reasoning_effort` is checked with `low`, which must succeed, and with an invalid value, which must return Pico HTTP 400, showing that the value reaches Pico as `reasoning.effort`. Thinking tests use Ollama `think:true` and `think:false` for each thinking model. The `think:false` subtests check bridge invariants on real output: no complete `<think>...</think>` pair remains in the answer when splitting, and `split_thinking: false` leaves the answer unsplit with empty reasoning. They do not require the model to write inline reasoning. An unknown model must return Pico HTTP 404 through all three APIs, with identical error data in raw and default modes and a body matching the direct Pico response. `PICO_TEST_BROKEN_MODEL` optionally selects another model expected to return a Pico error; all three APIs compare raw and default errors with a direct Pico HTTP response, and a default chat comparison checks that the next model succeeds. A separate 1000 ms, concurrency 2 comparison checks timeout sequencing, then checks server information and short chat generation.

The shipped plugin has no dependencies or build step. Plugin directory review holds lockfile installs, zip uploads do not install dependencies, and the SDK bundle exceeds the review limit of 256 KiB per file. Keeping the SDK in `dev/` keeps the plugin zip and MCPB self-contained with readable JavaScript.

To switch a future shipped build to the SDK v2 adapter:

1. Move exact pinned `@modelcontextprotocol/server` and its required dependencies from `dev/package.json` to root `package.json` dependencies, and add a root `package-lock.json`.
2. Change `server/index.js` to call `startWithSdk` with the v2 modules as `dev/sdk-entry.js` does.
3. Change CI to install and package production dependencies.
4. Recheck package size and conformance in all three client modes.

Default chat and Responses results and comparison rows include a redacted `refusal`. Chat accepts refusal-only messages with null or absent content; Responses joins string `refusal` parts in output order. Ollama comparison rows always include `usage: {prompt_eval_count, eval_count}`, using nulls for absent counts. `PICO_MAX_CONCURRENT_REQUESTS` requires a safe integer of at least 1.
